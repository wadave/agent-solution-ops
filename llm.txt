# AI Agent Instruction Manifest

This document provides a structured guide for AI agents to interact with this repository's toolchain. The primary interface is through `make` targets, which orchestrate all major development and operational tasks.

## Repository Structure

*   `iac/`: Contains all Infrastructure as Code (IaC) configurations, primarily using Terraform.
*   `services/`: The root folder for service instance folders. Each service may have its own `AGENTS.md` or `GEMINI.md` for more specific instructions.
*   `libs/`: Contains folder-based shared libraries that are accessible to the entire repository.

## General Workflow

The standard workflow for a developer or agent is as follows:

1.  **Onboarding (First time only):**
    1.  `make login` (from `iac/`) - Authenticate with GCP. For non-interactive login, use `make login project=<project_id>`.
    2.  `make init` (from `iac/`) - Initialize Terraform, set up shared state, and create `config.tfvars`. See `init` command details below for interactive vs non-interactive usage.
    3.  `add-environment-sa-to-tf-permissions` (from `iac/`) - Add the local development environment-related service account to the local Terraform permissions.
    4.  `add or update test user emails` (from `iac/`) - Edit the `test_user_emails` Terraform variable in `iac/config.tfvars`.
    4.  `make plan` (from `iac/`) - Review the initial infrastructure plan.
    5.  `make happen` (from `iac/`) - Deploy the base infrastructure.
2.  **Daily Development:**
    1.  `make login` (from root or `iac/`) - Refresh GCP credentials if needed.
    2.  `make config-pull` (from `iac/`) - Sync with any remote configuration changes.
    3.  Make code or Terraform changes.
    4.  `make plan` (from `iac/`) - Preview infrastructure changes.
    5.  `make happen` (from `iac/`) - Apply infrastructure changes.
    6.  `make config-push` (from `iac/`) - If `config.tfvars` was changed, push it for the team.
3.  **Cleanup:**
    1.  `make disappear` (from `iac/`) - Destroy all managed infrastructure.

## Secrets and Environment Variable Management

All secrets and environment variables used during building, development testing, and runtime are managed by Terraform.

The `iac/gcp_secrets.tf` file contains secrets that are explicitly created and managed by Terraform. These secrets are prefixed with the application namespace to avoid resource clashes with other deployments in the same project. These secrets are created in the map "secrets".

Secrets are mapped to individual modules using the "shared_secrets" attribute, and environment variables are mapped using the "environment_variables" attribute. Both are typically sub-attributes of a `cloudrun` map or an `agent_engine` map (see `iac/modules_5_nextjsui_agent_root.tf` and `iac/modules_3_agent_root.tf` for examples of mapping secrets to a service).

When secrets and environment variables are mapped this way, applying the Terraform configuration ensures:
*   Secrets are securely mapped to the services at runtime (using dedicated IAM grants per-secret/per-accessing-service-account).
*   Secrets and environment variables are made visible in local development (typically found in `scripts/dev/base_env.sh` and `scripts/dev/base_secrets.sh` within your service's implementation folder).

When asked to add a secret, first identify if it's a secret to be managed by Terraform (add to `iac/gcp_secrets.tf` and map to the target service), or if it's an existing secret to be accessed by Terraform (only map to the target service), then proceed accordingly.

## Command Reference

### Authentication

*   **Command:** `login`
*   **Directory:** `iac/` (or repository root)
*   **Description:** Authenticates with Google Cloud CLI and Application Default Credentials (`gcloud auth login --update-adc`) . This is a required first step.
*   **Usage:** 
    *   Interactive: `cd iac && make login`
    *   Non-interactive: `cd iac && make login project=<project_id>`, for example ```cd iac && make login project=my-project-id```.
*   **Agent Workflow:**
    *   **First-time login:** The agent MUST prompt the developer for the `project_id` and use the non-interactive mode.
    *   **Subsequent logins:** `make login` can be run from the repository root without the `project` parameter, as the gcloud project configuration will be cached in ./iac/build/base_env.sh.
*   **Prerequisites:** Must be run inside the dev container.
*   **Side Effects:** Creates/updates gcloud authentication tokens. Prompts the user for interactive browser-based login. Configures the active gcloud project.

### Infrastructure Lifecycle (iac/)

*   **Command:** `init`
*   **Directory:** `iac/`
*   **Description:** Initializes the Terraform environment. On first run, it creates a GCS bucket for shared state, and generates `iac/config.tfvars`. On subsequent runs, it configures the backend to use the existing GCS bucket.
*   **Usage:** 
    *   Before running, check `iac/backend.tf`.
    *   If the `bucket` value is `__GCP_TFSTATE_BUCKET__`, run `make init` with arguments: `cd iac && make init project=<project_id> region=<gcp_region> app_name=<app_name>`, for example ```cd iac && make init project=my-project-id region=us-central1 app_name=my-app```.
        *   The `app_name` will be used as a prefix for all resources. It MUST:
            *   Be less than 15 characters.
            *   Not contain "google" or variations like "g00gl3".
            *   Only contain lowercase letters, numbers, and hyphens.
            *   Begin with a letter and end with a letter or number.
    *   If the `bucket` value is already set, run without arguments: `cd iac && make init`. This will be non-interactive.
*   **Prerequisites:** Successful `make login`.
*   **Side Effects:** Creates `iac/config.tfvars`. Initializes Terraform (`.terraform` directory). May create a GCS bucket.

*   **Command:** `plan`
*   **Directory:** `iac/`
*   **Description:** Generates and displays an execution plan for Terraform. Shows what infrastructure changes (creations, updates, deletions) will be made.
*   **Usage:** `cd iac && make plan`
*   **Prerequisites:** `make init` has been completed.
*   **Side Effects:** Creates a Terraform plan file. Does not modify any cloud resources.

*   **Command:** `happen`
*   **Directory:** `iac/`
*   **Description:** Applies the changes defined in the Terraform configuration to the target GCP project. The name is a creative substitute for `apply`.
*   **Usage:** `cd iac && make happen`
*   **Prerequisites:** `make init` has been completed. It is best practice to run `make plan` first.
*   **Side Effects:** Creates, updates, or deletes resources in GCP. This is a state-modifying operation.

*   **Command:** `disappear`
*   **Directory:** `iac/`
*   **Description:** Destroys all infrastructure resources managed by Terraform in the GCP project.
*   **Usage:** `cd iac && make disappear`
*   **Prerequisites:** `make init` has been completed.
*   **Side Effects:** **DESTRUCTIVE**. Removes all managed cloud resources.

### Configuration Management (iac/)

*   **Command:** `config-push`
*   **Directory:** `iac/`
*   **Description:** Uploads the local `iac/config.tfvars` file to the shared GCS backend, allowing other team members to access it.
*   **Usage:** `cd iac && make config-push`
*   **Prerequisites:** `iac/config.tfvars` has been modified locally.
*   **Side Effects:** Overwrites the `config.tfvars` file in the GCS bucket.

*   **Command:** `config-pull`
*   **Directory:** `iac/`
*   **Description:** Downloads the latest `iac/config.tfvars` file from the shared GCS backend, overwriting the local version.
*   **Usage:** `cd iac && make config-pull`
*   **Prerequisites:** `make init` has been completed.
*   **Side Effects:** Overwrites the local `iac/config.tfvars` file.

### Dependency and State Management

*   **Command:** `upgrade`
*   **Directory:** `iac/`
*   **Description:** Updates all remote Terraform modules (e.g., from git) to the latest version specified in their source strings.
*   **Usage:** `cd iac && make upgrade`
*   **Prerequisites:** `make init` has been completed.
*   **Side Effects:** Modifies the downloaded module source code in the `.terraform` directory.

*   **Command:** `clean`
*   **Directory:** `iac/`
*   **Description:** Resets the local workspace by removing Terraform state files, downloaded modules, Python virtual environments, and Node.js modules. Does not affect cloud resources.
*   **Usage:** `cd iac && make clean`
*   **Prerequisites:** None.
*   **Side Effects:** Deletes local build artifacts and state files (e.g., `.terraform*`, `venv/`, `node_modules/`).

### Utility Commands

*   **Command:** `mod-graph`
*   **Directory:** `iac/`
*   **Description:** Generates a dependency graph visualization of only the high-level Terraform modules.
*   **Usage:** `cd iac && make mod-graph`
*   **Prerequisites:** `make init` has been completed. `graphviz` tool is installed.
*   **Side Effects:** Creates a `.png` image file in the `docs/` directory.

*   **Command:** `graph`
*   **Directory:** `iac/`
*   **Description:** Generates a full dependency graph of all low-level Terraform resources.
*   **Usage:** `cd iac && make graph`
*   **Prerequisites:** `make init` has been completed. `graphviz` tool is installed.
*   **Side Effects:** Creates a `.png` image file in the `docs/` directory.

*   **Command:** `external`
*   **Directory:** repository root
*   **Description:** Creates a self-contained, distributable archive of the repository. It downloads all remote dependencies (git-based Terraform modules and Python libraries) into the local filesystem and cleans up internal links.
*   **Usage:** `make external`
*   **Prerequisites:** The project is in a fully working state.
*   **Side Effects:** Creates a `repo_export.zip` file in the `exports/` directory.

### Service Account Management (iac/)

*   **Command:** `add-environment-sa-to-tf-permissions`
*   **Directory:** `iac/` or repository root
*   **Description:** Adds the local development environment-related service account to the local Terraform permissions by running `make get-sa` from the repository root or `iac` directory and adding its value to the env_sas array variable in `iac/config.tfvars`.
*   **Usage:**
    1.  Check if `iac/config.tfvars` exists. If not, run `make init` from `iac/` to onboard the project.
    2.  Run `make get-sa` from the `iac` directory or repository root to get the local development environment-related service account email.
    3.  Add the obtained service account email to the `env_sas` variable in `iac/config.tfvars`.
    4.  Run `make config-push` from the `iac` directory to push the updated configuration.
*   5.  Run `make plan && make happen` from the `iac` directory to apply new resources changes if any changes were applied to `iac/config.tfvars` in checking/adding the service account.
*   **Prerequisites:** `make init` has been completed in `iac/`.
*   **Side Effects:** Modifies `iac/config.tfvars` and updates the shared GCS backend.  Updates Terraform resources based on var.env_sas service account email array.

### Test User Management (iac/)

*   **Command:** `add or update test user emails`
*   **Description:** Edit the `test_user_emails` Terraform variable in `iac/config.tfvars`.
*   **Workflow:**
    1.  Edit the `test_user_emails` variable in `iac/config.tfvars`.
    2.  Run `make config-push` from the `iac` directory to push the updated configuration.
    3.  Run `make plan && make happen` from the `iac` directory to apply new resources changes if any changes were applied to `iac/config.tfvars`.

### Agent Creation

This section describes how to create new sub-agents. There are two types of sub-agents:

*   **Local/Folder-based Sub-agent:** A lightweight agent that is defined in a sub-folder of an existing agent and is deployed as part of the parent agent's service.
*   **Deployed Remote Sub-agent:** A full-fledged agent with its own service and deployment, which can be discovered and used by other agents.

When asked to create a sub-agent, first ask the user which type of sub-agent they want to create.

*   **Command:** `Create a new sub-agent`

#### Local/Folder-based Sub-agent Creation

*   **Description:** Creates a new local/folder-based sub-agent within an existing agent.
*   **Workflow:**
    1.  Ask the user for the canonical name of the parent agent that will host the new sub-agent.
    2.  Identify the parent agent's source code directory (e.g., `services/agent-root`).
    3.  Ask the user for the canonical name of the new sub-agent.
    4.  Ask for the reference sub-agent to copy as a starting template, or pick one or the user doesn't care.
    5.  Copy the existing sub-agent directory into the new directory for the sub-agent in the parent agent's `src/agents/` directory (e.g., copy from `services/agent-root/src/agents/<existing-sub-agent-name>` to `services/agent-root/src/agents/<new-sub-agent-name>`).
    6.  Edit the agent.py in the new the new sub-agent's directory with the implementation of the new agent.  Do not change the model settings.  The model should be gemini-2.5-flash.
    7.  Update the `__init__.py` file in the parent agent's `src/agents/` directory to import and register the new sub-agent.

#### Deployed Remote Sub-agent Creation

*   **Description:** Creates a new deployed remote sub-agent by copying and modifying an existing sub-agent.
*   **Workflow:**
    1.  Identify the *Source Terraform in the iac directory*. For example, file pattern "iac/modules_XXXX_agent_sub_YYYY.tf", where XXXX is the numbered module file index, and YYYY is the short canonical name of the agent using underscores instead of dashes/spaces.
    2.  Identify the *Source Agent code implementation directory*. For example, folder pattern "services/AAAA", where AAAA is the canonical name of the agent using dashes instead of underscores/spaces.
    3.  Copy the *Source Terraform in the iac directory* and increment the numbered module index to the next increment based on all modules_* files in the `iac` folder.
    4.  Edit the new file's "Service Configuration" details to be unique.
    5.  Copy the *Source Agent code implementation directory* folder into a new folder in the `services` directory matching the canonical name of the new agent using dashes instead of underscores/spaces.
    6.  Edit pyproject.toml in the new folder and update the description of the agent.  Never change the name away from "src".
    7.  Edit src/agent.py in the new folder and update the name and description of the agent.  Update the prompt with a reasonable default implementation based on the new agent's purpose.  Do not change the model settings.  The model should be gemini-2.5-flash.
    8.  Perform a dry-run of Terraform by running "make plan" in the `iac` directory.
    9.  Deploy the new agent using "make happen" in the `iac` directory.

### Agent Hierarchy Diagram

*   **Command:** `Create or update the agent hierarchy diagram`
*   **Description:** Generates a MermaidJS system diagram representing the hierarchy of agent instantiations, including all tools and sub-agents and their relationships. The diagram is then embedded in the `README.md` file under the "1. Overview" section, along with a brief summary. This process involves analyzing `agent.py` files to determine tool and sub-agent hierarchies, and using Terraform to see discovery dependencies between agents.
*   **Workflow:**
    1.  Analyzes the Terraform files in the `iac/` directory to determine the agent hierarchy.
    2.  Generates a MermaidJS sequence diagram based on the identified agent relationships.
    3.  Updates the `README.md` file to include the diagram and a summary.

*   **Command:** `Create or update the services and agents diagram`
*   **Description:** Generates a MermaidJS diagram showcasing Gemini Enterprise and its connections to agents, and agents with their sub-agents and tools, along with Cloud Run services and datastores, then adds it to the `README.md` in the overview section.
*   **Workflow:**
    1.  **Analyze Terraform Configuration:** Scan `iac/modules_*.tf` files to identify all deployed resources, such as Cloud Run services (agents, data ingestion, APIs), Vertex AI Search datastores, and Firestore databases, by looking for module sources that indicate what is being deployed (e.g., `agent-engine-adk`, `cloudrun-fastapi`, `vais-gcs-datastore`). This maps the high-level infrastructure.
    2.  **Identify Agent Implementations:** For each agent service identified in Terraform, locate the corresponding service implementation directory under `services/`. For example, a Terraform module defining a service with the slug `agent-hrbp` would correspond to the `services/agent-hrbp/` directory.
    3.  **Analyze Agent Structure:** Within each agent's service directory, analyze the `src/` folder by examining the main `agent.py` file to identify the agent's primary tools and description, and checking for a `src/agents/` subdirectory, which indicates the presence of sub-agents.
    4.  **Analyze Sub-Agents:** For each sub-agent found in the `src/agents/` directory, examine its own `agent.py` to identify its specific tools and purpose. This is a recursive discovery process.
    5.  **Map Tool-to-Datastore Connections:** Analyze the tools for agents and sub-agents to find code that interacts with datastores (e.g., calls to Discovery Engine clients or functions like `search_...`), using Terraform files to find clues by mapping secrets like datastore IDs to the agent services.
    6.  **Construct Diagram:** Based on all the gathered relationships (Gemini Enterprise -> Agents -> Sub-agents -> Tools -> Datastores, etc.), construct a comprehensive MermaidJS graph.
    7.  **Update README:** Read the `README.md` file, locate the "Overview" section, and replace the existing MermaidJS diagram with the newly generated one.

### NextJS UI Management

*   **Command:** `Enable the NextJS UI for an agent`
*   **Description:** Creates or enables a NextJS UI for an existing agent.
*   **Prerequisites:** Before proceeding, please ensure the following prerequisites from the `README.md` are met:
    *   The GCP Project's OAuth Consent Screen is configured. See [Configuring OAuth Consent Screen](/docs/assets/oauth-consent/README.md).
    *   OAuth Client Credentials are created, and authorized domains and redirect URLs are set up. See [Creating OAuth Client Credentials](/docs/assets/oauth-creds/README.md).
    *   The OAuth Client ID is stored as a secret named "OAUTH_CLIENT_ID" (or the value of `oauth_client_id_secret_name` from `iac/config.tfvars`). See [Storing OAuth Client ID as a Secret in Secret Manager](/docs/assets/oauth-client-id-secret/README.md).
*   **Pattern:** Agent modules (e.g., `modules_3_agent_root.tf`) define agents. A corresponding UI module (e.g., `modules_5_nextjsui_agent_root.tf`) can provide a web interface for it. The link between them is a local variable in the UI module's file, `agent_engine_agent_module_`, which must point to the correct agent module instance (e.g., `module.adk_agent_engine_3`).
*   **Workflow:**
    1.  Identify the target agent's Terraform file by matching the canonical name. For example, for the `root` agent, the file would be `iac/modules_3_agent_root.tf`.
    2.  Check if a corresponding NextJS UI Terraform file exists using the pattern `iac/modules_*_nextjsui_agent_YYYY.tf`, where `YYYY` is the agent's canonical name.
    3.  **If the file exists:**
        *   Ensure the module is not commented out.
        *   Verify that the `agent_engine_agent_module_` local variable points to the correct agent module instance identified in step 1.
    4.  **If the file does not exist:**
        *   Identify a source NextJS UI module to copy (e.g., `iac/modules_5_nextjsui_agent_root.tf`).
        *   Determine the next available module index `XXXX` by finding the highest numbered `modules_*.tf` file in the `iac` directory and incrementing it.
        *   Create the new filename using the pattern `iac/modules_XXXX_nextjsui_agent_YYYY.tf`.
        *   Copy the source file to the new filename.
        *   In the new file, update all numerical suffixes in the local variables and resource names to match the new module index `XXXX`.
        *   Update the "Agent Configuration" and "Service Configuration" sections with unique values for the new UI.
        *   Set the `agent_engine_agent_module_` local variable to point to the target agent module instance from step 1.
    5.  If any files were created or changed, run `make plan` and then `make happen` from the `iac` directory to deploy the changes.

### Gemini Enterprise UI Management

*   **Command:** `Enable Gemini Enterprise UI for an agent`
*   **Description:** Creates or enables a Gemini Enterprise UI for an existing agent.
*   **Prerequisites:** Before proceeding, please ensure the following prerequisites from the `README.md` are met:
    *   The GCP Project's OAuth Consent Screen is configured. See [Configuring OAuth Consent Screen](/docs/assets/oauth-consent/README.md).
    *   OAuth Client Credentials are created, and authorized domains and redirect URLs are set up. See [Creating OAuth Client Credentials](/docs/assets/oauth-creds/README.md).
    *   The OAuth Client ID and Client Secret are stored as secrets. See [Storing OAuth Credentials in Google Cloud Secret Manager](/docs/assets/oauth-client-id-secret/README.md).
    *   The `gemini_enterprise_app_id` in `iac/config.tfvars` is set to a valid value. If it is "unset", you will be prompted to provide a valid ID.
*   **Pattern:** Agent modules (e.g., `modules_3_agent_root.tf`) define agents. A corresponding Gemini Enterprise UI module (e.g., `modules_6_gemini_enterprise_agent_root.tf`) registers the agent with Gemini Enterprise. The link is established through a `depends_on` block in the Gemini Enterprise module, which must reference the correct agent module instance (e.g., `module.adk_agent_engine_3`).

*   **Workflow:**

    1.  Identify the target agent's Terraform file by matching the canonical name (e.g., for the `root` agent, the file is `iac/modules_3_agent_root.tf`).
    2.  Check if a corresponding Gemini Enterprise UI Terraform file exists using the pattern `iac/modules_*_gemini_enterprise_agent_YYYY.tf`, where `YYYY` is the agent's canonical name.
    3.  **If the file exists:**
        *   Ensure the module is not commented out.
        *   Verify that the `depends_on` block correctly references the agent module instance from step 1.
    4.  **If the file does not exist:**
        *   Identify a source Gemini Enterprise UI module to copy (e.g., `iac/modules_6_gemini_enterprise_agent_root.tf`).
        *   Determine the next available module index `XXXX` by finding the highest numbered `modules_*.tf` file in the `iac` directory and incrementing it.
        *   Create the new filename using the pattern `iac/modules_XXXX_gemini_enterprise_agent_YYYY.tf`.
        *   Copy the source file to the new filename.
        *   In the new file, update all numerical suffixes in the local variables and resource names to match the new module index `XXXX`.
        *   Update the configuration sections with unique values for the new UI.
        *   Ensure the `depends_on` block in the new module correctly references the target agent module instance from step 1.
    5.  If any files were created or changed, run `make plan` and then `make happen` from the `iac` directory to deploy the changes.

### Rebrand for a new company or domain

*   **Command:** `Rebrand for a new company or domain`
*   **Description:** Updates the demonstration's branding to a new company and domain.
*   **Workflow:**
    1.  Ask the user for the target company name and a brief description of the company or its domain (e.g., "Bank of Cymbal", "financial services").
    2.  Use tools like `codebase_investigator` or `glob` to find all `agent.py` files within the `services/` directory. These files are the most likely to contain hardcoded agent prompts, personas, and company descriptions.
    3.  Iterate through each `agent.py` file found. Read the contents of each file to identify any company-specific names, descriptions, or domain-specific language.
    4.  Carefully replace the old branding with the new branding in each identified file, ensuring the agent's persona and instructions remain coherent.
    5.  Search the primary frontend application directory (often named `services/nextjsui-...`) for any hardcoded UI text, logos, or styles related to the old brand and update them.
    6.  Finally, update the `README.md` file to reflect the new branding.
